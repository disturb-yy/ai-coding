# 项目规约编写指南

本文件面向参与此项目的模型和开发者。它说明如何先读取项目结构，再把稳定、可验证的协作规则写入
`AGENTS.md`。它不是业务需求、迭代计划或临时任务清单。

## 阅读顺序

每次修改前，按以下顺序建立上下文：

1. 读取本文件，了解规约的结构与维护方式。
2. 读取仓库根 `AGENTS.md`，确认模块依赖、目录职责和全局禁止项。
3. 找到目标模块，读取该模块的 `AGENTS.md`，确认模块内部边界。
4. 读取根 `pom.xml` 和目标模块 `pom.xml`，以实际 Maven 依赖验证文字规则。
5. 读取目标包的生产代码与同路径测试，复用既有命名、异常和测试习惯。
6. 修改后执行 `mvn clean verify`；架构变化还应确认 ArchUnit 规则覆盖了新边界。

当文字规约与实际构建依赖冲突时，先停止改动并明确冲突；不要悄悄绕过规约或加入反向依赖。

## 先确定代码属于哪里

先回答“谁拥有这条业务规则”，再决定目录。使用下面的判断表：

| 问题 | 应放模块 | 示例 |
| --- | --- | --- |
| 是否允许订单确认、取消或状态迁移？ | `domain` | `order.confirm()` |
| 外部调用者传入和获得什么数据？ | `api` | Command、Query、View、服务接口 |
| 一个用例如何加载、调用并保存聚合？ | `app` | 创建、确认订单的用例编排 |
| 如何访问数据库、消息系统或外部服务？ | `base` | 仓储实现、HTTP/RPC Adapter |
| 如何接收 HTTP 请求并组装 Bean？ | `main` | Controller、配置、启动入口 |

禁止用“方便调用”作为跨层依赖的理由。特别是 `app` 不依赖 `base`，`domain` 不依赖任何项目模块，
Controller 不依赖 `app` 的具体实现。

## AGENTS.md 应写什么

根 `AGENTS.md` 只记录长期有效的项目规则：

- 模块依赖方向与架构边界；
- 根目录、模块、生产代码、测试和资源目录的职责；
- 代码放置和禁止项；
- 必须执行的验证命令和架构检查；
- 指向模块级规则或设计文档的导航。

模块级 `AGENTS.md` 只记录该模块的所有权：允许的类型、推荐包、禁止的框架或依赖、以及必须维持的
不变量。例如 `domain` 规定聚合通过行为维护状态，`base` 规定持久化实现不泄漏给 `app`。

不要把以下内容写入 `AGENTS.md`：某一期需求状态、未确认的 TODO、临时发布步骤、个人偏好、重复的 API
字段定义，或无法由测试、构建和代码审查验证的空泛口号。业务需求应放在需求文档，具体接口应放在 `api`。

## 目录规约的层次

```text
仓库根                         聚合构建和跨模块规则
└── 模块根                     模块 POM、模块规则、模块源码
    ├── src/main/java           该模块生产代码
    ├── src/test/java           对应生产包的测试和架构测试
    └── src/main/resources      配置或模块私有资源
```

模块内部的包只用于职责分组，不改变模块边界：

| 模块 | 推荐包 | 不能放入 |
| --- | --- | --- |
| `domain` | `model`、`repository`、`event` | Controller、Mapper、Spring 配置 |
| `api` | `command`、`query`、`view`、`service` | 领域实体、实现逻辑、Spring 注解 |
| `app` | `service`、`assembler` | SQL、Mapper、Adapter、聚合 setter |
| `base` | `repository`、`client`、`messaging` | 领域规则、被 app 直接调用的实现 |
| `main` | `bootstrap`、`config`、`web` | 领域规则、持久化实现、API 实现类 |

本示例规模较小，现有类可直接放在模块根包。只有同类职责形成清晰集合时才建立子包，且移动后必须保持
Java 包名与目录一致。

## 将规则变成可验证约束

`AGENTS.md` 是协作提示，不是唯一的防线。每增加一条关键规则，都判断是否可用下列方式自动验证：

| 规则类型 | 优先验证方式 |
| --- | --- |
| Maven 模块依赖方向 | `pom.xml` 依赖声明和 Maven Enforcer |
| Java 包或类依赖 | ArchUnit |
| 领域状态迁移和不变量 | 聚合单元测试 |
| 应用用例编排 | 应用层单元测试 |
| HTTP 契约与映射 | Web 层测试或集成测试 |

如果规则暂时不能自动验证，先把它写成具体、可审查的禁止项；不要写成“保持代码优雅”这类无法判断的句子。

## 修改规约的流程

1. 先通过现有 `AGENTS.md`、POM 和代码确认当前事实。
2. 只在新能力确实改变长期边界时修改根规约。
3. 同步更新受影响模块的 `AGENTS.md` 和 README 中的导航或职责表。
4. 若新增或调整依赖边界，同时新增或调整 ArchUnit/Maven 检查。
5. 运行最小相关测试，最后运行 `mvn clean verify`。
6. 在提交说明中写清规则为何变化、影响哪个模块、使用了哪些验证。

## 修改前检查清单

- [ ] 我已读取根和目标模块的 `AGENTS.md`。
- [ ] 我能说明目标代码属于哪个模块，以及为什么不属于其他模块。
- [ ] 新依赖符合 `main -> api/app/base`、`app -> api/domain`、`base -> domain`。
- [ ] 领域状态只由聚合行为改变，没有从应用层调用 setter。
- [ ] 新规约是长期规则，且已同步到需要它的文档和测试。
- [ ] 我已执行与改动相称的 Maven/ArchUnit 验证。
